Semantica sumelor in DB (confirmata la planificare in `sql/refactor/REFACTOR_FINANCIAL.sql:1-47`): `suma_initiala` = total facturat (dupa reducere); `suma` = rest de plata, recalculat de functia `recalculare_stare_plata` (declansata de trigger-ul pe `tranzactii`) ca `suma_initiala - SUM(tranzactii.suma unde plata_id = ANY(plata_ids))`, iar statusul devine 'Achitat' cand restul <= 0.01. Deci "Total incasat" se afiseaza ca `suma_initiala - suma` (valoare mentinuta de server), nu ca suma bruta a tranzactiilor (o tranzactie poate acoperi mai multe facturi).

Actiunea rapida "Marchează Achitat cu X RON" (D-08) — decizie de proiectare, fara logica noua de business:
- X implicit = restul de plata. X == rest (±0.01) → doar RPC-ul existent `proceseaza_plata_factura` (acelasi folosit de butonul "Încasează Rapid" din PlatiScadente.tsx:518 si GestiuneFacturi.tsx:427).
- X < rest → clientul a platit mai putin si factura trebuie inchisa: intai update whitelist `{ suma_initiala: veche - (rest - X), suma: X }` (corectie a sumei facturate, afisata explicit inainte de confirmare), apoi acelasi RPC cu X → trigger-ul aduce restul la 0 si statusul la 'Achitat'.
- X > rest → blocat (avansurile se fac din Jurnal Încasări).
- Dupa operatie: refetch factura + tranzactia noua prin id (model PlatiScadente.tsx:531-541), iar daca statusul real nu e 'Achitat', utilizatorul primeste avertisment explicit cu statusul real (protectie fata de diferente intre DB live si fisierele SQL din repo).
