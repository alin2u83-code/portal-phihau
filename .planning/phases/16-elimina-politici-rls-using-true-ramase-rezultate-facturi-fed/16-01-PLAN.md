<objective>
Elimina ultimele politici RLS periculoase de tip `USING(true)` ramase pe DB live (proiect
Supabase `wuhidifzsutwgdfkwhmd`), confirmate prin interogare directa pe `pg_policies` (nu prin
auditul static pe migratii locale, care era divergent de starea reala a DB). Trei fix-uri, in
aceeasi migratie SQL:

1. **`public.users` (SEC-03)** — politica `authenticated_read` este
   `FOR SELECT TO authenticated USING (true)`: orice utilizator autentificat (inclusiv SPORTIV)
   poate citi INTREG tabelul users (coloane `id`, `email`, `tema_config`). Fix: restrictioneaza
   SELECT la `id = auth.uid() OR public.is_super_admin()`. Politica separata `own_row_update`
   (UPDATE scope `id = auth.uid()`) e corecta si NU se atinge.

2. **`public.knowledge_base` (SEC-04)** — toate operatiile (SELECT/INSERT/UPDATE/DELETE) sunt
   `USING(true)`/`WITH CHECK(true)` pentru rolul `authenticated`. Aceasta e baza de cunostinte a
   asistentului AI (RAG): orice utilizator autentificat poate insera/edita/sterge articole
   (risc de integritate/vandalism, nu doar expunere). Fix: pastreaza SELECT deschis tuturor
   utilizatorilor autentificati (continut de ajutor partajat, sensibilitate mica), dar
   restrictioneaza INSERT/UPDATE/DELETE la `public.is_super_admin()`.

3. **`public.fisa_inscriere` (SEC-05, severitate HIGH)** — are doua politici permisive:
   `Bypass_Super_Admin` (corecta) SI `Club_Admin_Examen_Access`
   (`EXISTS(... rol_denumire = 'ADMIN_CLUB')`) — a doua verifica DOAR rolul, cu ZERO scoping de
   club. Coloanele includ date GDPR medicale/familiale (`antecedente_medicale`, `grupa_sangvina`,
   `rh`, `nume_tata`/`nume_mama`/`profesie_*`, `acord_gdpr`, `acord_publicare_foto`,
   `cale_fisier_pdf`). Rezultat: orice ADMIN_CLUB din ORICE club citeste/scrie datele medicale ale
   copiilor din TOATE celelalte cluburi — mai sever decat scurgerea financiara din Phase 15 (date
   medicale vs bani). Fix: scope-uieste `Club_Admin_Examen_Access` la sportivii propriului club
   activ via lantul FK `practicant_id -> sportivi.club_id = public.get_active_club_id()`.
   FK-ul si numele coloanelor (`sportivi.id`, `sportivi.club_id`) se VERIFICA pe schema live
   inainte de a scrie predicatul — NU se presupun.

Purpose: elimina ultimele cai de scurgere/alterare de date sensibile (email-uri utilizatori, baza
de cunostinte AI, date medicale GDPR) intre utilizatori si intre cluburi (7 cluburi reale in
productie). Output: o migratie SQL noua aplicata live + verificare in `pg_policies` + verificare
umana fara regresie.
