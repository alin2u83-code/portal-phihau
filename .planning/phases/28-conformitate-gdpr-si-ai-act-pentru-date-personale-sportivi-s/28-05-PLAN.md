<gotchas>
1. **`currentUser.id` NU este id-ul de sportiv in mod garantat si NU este `auth.uid()`.** In `hooks/useDataProvider.ts` (~linia 300), `setCurrentUser` face spread peste profilul de sportiv al contextului activ; pentru un utilizator FARA profil de sportiv, cade pe `session.user.id`. Sursa corecta si neambigua pentru id-ul de sportiv al utilizatorului curent este `activeRoleContext?.sportiv_id` — exact ce foloseste `hooks/useDataProvider.ts` la liniile 386-388. Foloseste asta, nu `currentUser.id` si nu o cautare in lista de sportivi.
2. **`procesat_de` si `procesat_la` NU se scriu din client.** Planul 01 a creat trigger-ul `tr_cereri_gdpr_procesare` care le seteaza server-side cu `auth.uid()` si `now()` la orice schimbare de status. Payload-ul de update din UI contine DOAR `status`. Daca trimiti si `procesat_de` din client, vei scrie un id de sportiv acolo unde se asteapta un id de utilizator auth.
3. **`cereri_gdpr` NU are coloana `motiv_respingere`.** `CereriInscriere.tsx` are un modal de respingere cu motiv; aici acesta se inlocuieste cu o confirmare simpla. Nu adauga coloana — nu e in lista blocata D-07.
4. **Aprobarea nu declanseaza nicio actiune pe date.** D-11 si Boundaries din SPEC.md resping explicit orice stergere sau export automat. Orice apel de stergere sau generare de fisier legat de `handleAproba` este in afara scope-ului si trebuie semnalat, nu implementat.
5. **`MenuItem.icon` este obligatoriu; `SubMenuItem` nu accepta icon.** In `adminMenu` si `adminClubMenu`, „Protecția datelor” intra ca `SubMenuItem` in submeniul „Setări & Admin” (fara icon). In `instructorMenu` si `sportivMenu` intra ca `MenuItem` de nivel superior (cu icon).
6. **Fara routing pe URL.** Navigarea in acest SPA se face exclusiv prin `activeView` din `NavigationContext`; nu introduce `react-router` pentru view-urile noi (CLAUDE.md).
</gotchas>
