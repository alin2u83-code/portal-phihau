Contracte create aici (consumator: 43-03 LoginParola). Nu redenumi.
- `trimiteCodResetParola(email: string): Promise<{ error: any }>` — normalizeaza `email.trim().toLowerCase()`, apeleaza `supabase.auth.resetPasswordForEmail(email)` (fara redirectTo, ca azi), apoi `inregistreazaEmailAuth('reset_parola', !error)`. try/catch: o exceptie => `inregistreazaEmailAuth('reset_parola', false)` si `{ error: exceptia }`. Nu arunca niciodata.
- `reseteazaParolaCuCod(email: string, cod: string, parolaNoua: string): Promise<{ user: any | null; error: any; etapa: 'cod' | 'parola' | null }>`:
  1. `supabase.auth.verifyOtp({ email: normalizat, token: cod.trim(), type: 'recovery' })`; eroare sau fara user => `{ user: null, error, etapa: 'cod' }`.
  2. `supabase.auth.updateUser({ password: parolaNoua })`; eroare => `await supabase.auth.signOut({ scope: 'local' })` (Pitfall 6: nu lasa sesiune de recovery fara parola) si `{ user: null, error, etapa: 'parola' }`.
  3. succes => `await revocaDispozitiveIncredere()` (din ./emailMfaService; parola schimbata => dispozitive invalide) si `{ user: data.user, error: null, etapa: null }`.
  Validarea parolei (`valideazaParola`, `checkLeakedPassword`) ramane la apelant. Serviciul NU face signOut la succes (LoginPage il face; zona externa pastreaza sesiunea).
- Existente: `inregistreazaEmailAuth(tip, reusit)` din services/authEmailAuditService.ts; `revocaDispozitiveIncredere()` din services/emailMfaService.ts l.172; `supabase` din supabaseClient.ts (are fallback process.env, deci serviciile se pot importa din Node/tsx dupa `import 'dotenv/config'`).
- LoginPage azi: handleForgotPassword l.85-101 (resetPasswordForEmail + mesaj neutru "Cod trimis daca adresa exista in sistem..." chiar si la eroare), handleVerificaCod l.103-150 (valideazaParola -> checkLeakedPassword -> verifyOtp recovery -> updateUser -> revocaDispozitiveIncredere -> signOut -> mesaj succes).
