<key_facts>
Diferențe critice de API între `<select>` nativ / `<Select>` și `SearchableSelect` (ui.tsx:760) — executorul TREBUIE să le respecte în fiecare conversie:

1. **onChange primește un string brut, NU un event.** Native: `onChange={e => setX(e.target.value)}` → SearchableSelect: `onChange={val => setX(val)}`.
2. **Opțiunea goală devine `emptyLabel` + `placeholder`.** Șterge `<option value="">Toate...</option>` explicit și pune `emptyLabel="Toate..."` (pentru select nativ pe mobil) ȘI `placeholder="Toate..."` (pentru câmpul desktop). Pe desktop starea goală = input gol + buton X de clear (deja implementat în componentă); nu se prepend-ează opțiune goală în listă.
3. **`options` = `{ value: string, label: string }[]`.** Mapează sursele existente în acest format. Valorile rămân IDENTICE cu cele curente (ex: `g.id`, `g.ordine.toString()`, luni ca `String(idx+1)`, ani ca `String(an)`) — nu schimba semantica valorii.
4. **SearchableSelect nu are `disabled` nativ** — vezi Task 1, se adaugă prop opțional `disabled`.
5. **Fallback mobil** (<768px) e deja built-in în SearchableSelect (select nativ) — nu adăuga logică proprie.
6. Nu introduce librării externe (constraint CLAUDE.md). Nu sparge API-ul public al componentelor existente (constraint CLAUDE.md).

Skill portal-debug: modificare de UI cu risc de regresie a comportamentului filtrelor — verifică fiecare conversie păstrează valoarea filtrului activ și opțiunea "toate/orice".
</key_facts>
